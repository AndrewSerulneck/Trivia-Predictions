## 1. Summary (plain English, for Andrew)

A new row in the Partner Dashboard menu, **Order Join Merch**, opens a white "store" panel that
slides up from the bottom, the same way the Partner Manual does. The store sells four items, each
printed with the Hightop Challenge QR code that guests scan to join and play:

| Item | Photo | How a partner picks a quantity | Price |
|---|---|---|---|
| Round Coasters | `public/store/web/coasters_round.webp` | Dropdown: 100 / 250 / 500 / 1,000 | $30 / $60 / $100 / $175 |
| Square Coasters | `public/store/web/coasters_square.webp` | Same dropdown | Same prices |
| Table Tents | `public/store/web/table_tents.webp` | − / + quantity box | $4 each |
| Table Card with Holder (one set = card + chrome holder) | `public/store/web/card_holders.webp` | − / + quantity box | $8 per set |

The store shows each line's price as the partner changes the quantity, and a running total in a bar
at the bottom. There is **no per-coaster ("24¢ each") price** — Andrew removed it 2026-10-01 as
unnecessary. Under the products, a **free "Print your own QR code" card** lets a partner download
the same join QR (PNG + SVG) for their own menus or table tops, at no charge. **Review order** shows the full order. **For now the final button reads "Ordering
opens soon" and does nothing.** No order is saved, no card is charged and no email is sent. The
store looks and behaves like a real one, so the shopping screens won't need rebuilding when you pick
a warehouse/shipping (3PL) company. That work only has to connect the last button.

The row appears for **every partner on the next deploy** (no on/off switch). This adds **no server
calls, no database tables and no new monthly cost** (see §6).

## 3. Design (UI/UX)

### 3a. Matching the photos' white

- Panel and body background: a new token **`--ht-store-paper: #FEFEFE`** in `app/globals.css`,
  exposed in Tailwind as `ht-store-paper`. The value is mirrored in `lib/themeTokens.ts` with a
  comment pointing at this section. Don't use a hard-coded `bg-[#FEFEFE]` in components.
- Every product `<img>` gets **`mix-blend-multiply`**. On a near-white canvas, multiply makes the
  photo's 1–2-level off-white disappear, so there is never a visible box around a photo, even if
  the background varies by a shade. Product photos sit **directly on the paper**: no card fill,
  no border around the photo.
- Text on the paper: slate-900 headings, slate-600 body, `ht-cyan-…`/indigo accents only where the
  brand colours already pass contrast on white (verify ≥ 4.5:1 for text). The panel scrim stays the
  dark `bg-slate-950/70`, like every other sheet.

### 3b. Layout (phone first, 390 px)

```
┌──────────────────────────────────────┐  ← OwnerSheet size="tall" tone="light"
│ ▬ (grab handle)                      │

│ Order Join Merch                     │
```

- **Coaster dropdown:** a native `<select>`, so iOS shows its wheel picker. The first option is
  "None". Each option reads `250 coasters — $60`. When a pack is chosen the line under it reads
  `250 coasters · $60.00`. **No per-coaster price** (decision 5).
- **Free QR card** (`components/owner/store/FreeQrDownload.tsx`), after the product list: QR preview,
  "Print your own QR code", where it goes (`play.hightopchallenge.com`), and two `<a download>`
  links: **Download PNG** (2050 px) and **SVG for printers**.
- **Stepper:** − / number field / +, `inputMode="numeric"`, clamped to 0–`MERCH_MAX_UNIT_QTY`.
  A typed value outside that range is corrected when the field loses focus, with no error shown.
  − is disabled at 0, + at the maximum.
- **Order bar:** this is the sheet's `footer`. It shows the item count and the subtotal. "Review
  order" is disabled until the cart has something in it. With an empty cart the bar reads
  "Choose a quantity to start an order".
- **Review step** (slides in from the right via `SlideSteps`): one row per line item showing name,
  quantity and line total; Subtotal; "Shipping & tax — Calculated at checkout"; **Estimated
  total**; "Ships to: {venue display name}". The footer is `WizardFooter` with StepBack ("Back to
  store") and a **disabled** Next labelled **"Ordering opens soon"**. A short note under the total
  says online ordering is coming soon and gives Andrew's contact line, which he must supply
  (open question Q2).
- **Desktop (`sm:`+):** the same sheet, centred, `max-w-2xl`. Products can go in two columns at
  `md:`. The phone layout is the priority.
- **Accessibility:** every photo has real alt text (from the catalog). The `<select>` and stepper
  have `<label>`s. Line totals are inside `aria-live="polite"`. The disabled final button uses
  `aria-disabled` plus visible explanatory text so it doesn't read as "broken". Reduced motion
  follows `SlideSteps`.

### 3c. Navigation behaviour

- The store is a **URL-mirrored dashboard sheet**, `?sheet=store` (Shop) and
  `?sheet=store&step=review`, like Schedule and Rewards, **not** local state like the Partner
  Manual. Reasons: it has two steps, so the phone's Back must step from Review to Shop to closed
  instead of leaving the dashboard with a cart open; and it gives a shareable deep link
  (`/owner/dashboard?sheet=store`) for future "re-order your coasters" emails.
- Menu row tap: close the drawer, then in the drawer's `onExited` call `pushSheet(window.history,
  window.location, "store")` (the same "wait for the drawer to release its scroll lock" reason the
  link rows already have). Never `router.push` a sheet step (CLAUDE.md).
- Landing on `?sheet=store&step=review` with an empty cart (reload, shared link) → `replaceStep`
  to Shop.

## 4. Data model (pure TypeScript, no database)

`lib/merchCatalog.ts`: **the one file to edit to change products, copy or prices.** It holds no
`server-only` code and is safe in the browser. Shape (final names are up to Phase 1, but keep the
intent):

```ts
type MerchPricing =
  | { kind: "pack"; packs: readonly { quantity: number; priceCents: number; sku: string }[] }
  | { kind: "unit"; unitPriceCents: number; maxQuantity: number; sku: string };

type MerchProduct = {
  id: "coasters-round" | "coasters-square" | "table-tents" | "table-card-set";
  name: string;            // "Round Coasters"
  description: string;     // placeholder copy, Andrew edits
  image: { src: string; width: number; height: number; alt: string };
  pricing: MerchPricing;
};
```

- **Money is integer cents everywhere.** Coaster packs are 3000/6000/10000/17500. Tents are 400.
  Card sets are 800. Formatting happens only at render, via `Intl.NumberFormat("en-US",
  { style: "currency", currency: "USD" })`. Never use floating-point dollars.
- **SKUs are placeholders** (e.g. `HTC-CST-RND-100`, `HTC-TENT`, `HTC-CARDSET`). The 3PL will have
  its own SKU scheme. Mapping to it is a Phase 5 job, and keeping the SKU next to each sellable unit
  now makes that a data change, not a refactor.
- `lib/merchPricing.ts` (pure): `lineTotalCents`, `cartSummary` (item count, subtotal),
  `clampUnitQuantity`, `isValidPack`, and **`buildMerchOrderDraft(cart, venue)`**, which returns
  the order object a 3PL/checkout call will eventually receive: `{ venueId, lines: [{ sku,
  productId, quantity, lineTotalCents }], subtotalCents, currency: "usd" }` (`quantity` = pieces;
  for a coaster pack the SKU names the pack; no per-piece price is derived — decision 5). The
  Review screen renders from this draft, so the future integration consumes exactly what the
  partner saw. Pricing is recomputed from the catalog, **never** trusted from UI state. (Phase 5
  will recompute it again on the server.)

### Phase 4.2 — Sheet history: "no step" is a real value; a corrected Review doesn't leave a duplicate entry (DONE 2026-10-01)
**Model: Opus 5.5 · Effort: high.** `lib/useOwnerSheet.ts` / `lib/ownerSheetParams.ts` are shared
with Schedule and Rewards. Their behaviour must not change except where the same bug applies.
Handoff: `docs/join-merch-store-plan_PHASE_4.2_HANDOFF.md`. As built: `goBack`/`stepBack` take
`string | null` and the store calls `nav.goBack(null)` (F4). `replaceCurrentStep` is **replaced** by
`correctStep(target)` (driver `correctStep()` in `lib/ownerSheetParams.ts`: pop when depth ≥ 2, else
replace; the hook guards against a second pop before the first lands). **Deviation:** it pops on depth
alone, not only "when the target is the previous screen" — the driver can't read the previous entry
and Rewards' detail has two possible parents; the screen popped to corrects itself in turn. Schedule and
Rewards had the same bug (detail → list, Review → Repeat → When, end → detail → list, and the reward
wizard's own "replace") and now use `correctStep` too. Verified in jsdom and in Chromium on `next start`.

- **F4 — "Back to store" writes `?step=shop`, then the effect rewrites it.** `nav.goBack("shop")`
  at depth < 2 replaces the URL with the literal `step=shop`, and `MerchStoreSheet`'s correction
  effect then replaces it again with no step (two `replaceState`s and an invalid URL in between).
  **Fix:** widen `UseOwnerSheetResult.goBack(previous: string | null)` and `stepBack(…, previous:
  string | null)` so `null` means "the sheet's first screen, no `step`". Call `nav.goBack(null)` in
  `MerchStoreSheet`. Update `tests/lib.owner-sheet-params.test.ts` and the store test (expects
  `goBack(null)`).
- **F3 — Reloading on Review leaves two identical Shop entries.** Shop (depth 1) → Review (depth 2)

  is now `[dashboard, ?sheet=store, ?sheet=store]`. The first phone Back seems to do nothing.
  **Fix:** when the step being corrected sits at depth ≥ 2 and the correction target is the
  previous screen, **pop** (`history.back()`) instead of replacing. Implement it once in
  `useOwnerSheet`, e.g. a `correctStep(target)` that pops or replaces, and use it from the store's
  effect. Then check whether Schedule's and Rewards' "a wizard step whose data a reload lost is
  corrected in place" has the same duplicate-entry problem. If it does, switch them too and update

## 6. Cost (global cost-conscious rule)

- **Phases 1–4.6 add zero server work:** no API route, no database read or write, no cron and no
  external API. The catalog is bundled JavaScript (a few KB). The free QR is two static files
  (≈ 3 KB PNG + 4 KB SVG) served by the CDN, so even 1,000 downloads a month is ≈ 7 MB.
- **The only recurring cost is image bandwidth from Vercel's CDN.** Unoptimized, one store open
  downloads ≈ 8 MB. With the Phase 1 WebP files it's ≈ 0.4–0.6 MB, and the browser caches it after
  the first view. At 100 partners × 3 opens/month that's ≈ 0.2 GB/month (vs ≈ 2.4 GB raw), which is
  negligible either way. Serving pre-optimized static files also avoids Vercel Image Optimization
  transformation charges. **Use `next/image` with `unoptimized`, or a plain `<img>` with
  width/height and `loading="lazy"`**, not on-the-fly optimization.
- Phases 5–6 will add per-order DB writes, Stripe fees and 3PL fees. Those get estimated when they
  are scheduled.
