# Speed Trivia variety policy v1

Frozen for Phase 2 on **2026-10-13 (New York)**. Policy ID: **`speed-subject-variety-v1`**. This is a specification and measured preparation; no application behavior or database status changed. Parent: [variety and backlog plan](speed-trivia-variety-and-backlog-plan.md).

## 1. Identity and evidence

A primary subject is a named person, performing/team group, or individually identified creative work/franchise whose identity or association is needed to answer the question. Keep **all** primary subjects in a relation, rather than trusting the model's single `primarySubject` label. A work used to identify its artist is a focus of that association; a decorative example or contrast is not. Exclude distractor options entirely. Read the prompt, correct answer and verified image context; a correct answer is evidence of identity, not automatically a person. Countries, materials, numbers, animals, occupations, genres, regions, techniques and other generic concepts do not acquire a person/work cooldown just because they repeat.

Store kind, stable canonical key, source spans/roles, related creator links, classifier/registry/policy versions and content hash. Separate `identified`, `generic` and `unknown`; report coverage rather than guessing the last category. No bare capitalization heuristic, shared surname, answer key or unchecked generator label is sufficient evidence. Newly generated named-entity candidates with unresolved identity/role are blocked before paid comparisons and saving, with `subject_identity_unresolved`; this is different from an unknown legacy row remaining usable in player selection.

Normalize Unicode/diacritics/punctuation and curated full-name/initial aliases. Preserve non-decomposing letters (e.g. Polish ł → l); the old normalizer loses this letter. Do not treat `Swift` alone as Taylor Swift, a royal queen as Queen, “Queen of Soul” as the band, a character as its author, or different works with the same short title as one work. Ambiguous aliases require contextual role evidence or remain unknown. Registry keys are category-independent; authors/artists in another category count identically.

When a fact concerns an artist's releases or a work's authorship, count the artist/author **and** the precise work. A different song label cannot bypass the artist limit. Related-creator expansion requires a reviewed, versioned relationship and a creator-focused relation in the prompt. An adaptation's cast, narrative technique or fictional setting does not automatically make every original creator a primary subject. Preserve separately identified primary people in multi-person facts; any blocked subject blocks generation. A creator relationship is not an alias equating the work with the person.

The bounded 87-identity registry and synthetic cases are [registry v1](fixtures/speed-trivia-variety-subject-registry-v1.json) and [evaluation v1](fixtures/speed-trivia-variety-evaluation-v1.json). They calibrate known examples; they do not fully tag the bank. Phase 2 must implement role validation and expand safe coverage with local evidence; this registry is not a closed allowlist: a new precise full name with unambiguous person/group/work role and source spans may establish a new canonical identity before the unchanged fact/soundness check; it must not ship the Phase 1 lexical reference measurement as a universal entity recognizer. Preserve raw names in content; normalization is for identity matching only.

## 2. Numeric generation contract

| Control | Frozen v1 value / meaning |
| --- | --- |
| Cooldown | **30 × 24 hours = 2,592,000,000 ms**; block when `0 <= now - lastSubjectAdmissionAt < duration`; eligible exactly at the boundary |
| Included recent history | All successful Speed admissions in **active, pending and retired** states, including internal holds; global across categories and writers |
| Clock | Server UTC instants; latest successful introduction of the subject in a content version. Status-only approval, hold, retirement or feature backfill does not reset it |
| Legacy clock | `created_at` is the explicitly labelled lower-bound proxy where no admission event exists; missing/invalid/future timestamps produce visible unknown-history diagnostics and block new generation for that identified key until resolved, not an invented recent event |
| Edits | Introducing a new subject in an admitted content edit starts its clock; same-content approval/metadata backfill does not. Preserve prior versions' subject history |
| Within accepted run | **At most 1 occurrence per identified person/group/work**, across every category; reserve every primary key after a successful save |
| Bank concentration | Block a generated candidate if **any identified primary subject already occurs in ≥24 current active + pending rows** (held pending included); count each row once per key |
| Retired concentration | Retired rows do not count toward the 24; they remain fact reservations and retain the 30-day cooldown |
| Ordering | Local schema/subject/clock/concentration checks **before** paid fact comparison; then unchanged uniqueness, soundness and signed admission before saving |
| Shortfalls | Fewer admissions, including zero, are valid; no budget, subject or fact-policy relaxation to fill a target |
| Existing ceilings | $0.50/operation, ≤100 accepted, ≤200 candidates, ≤20 generation calls, ≤25 requested per batch, 600,000 ms operation deadline; existing request/token/retry ceilings remain |

The threshold **24** is the measured upper-quartile concentration among the 87 registered identities (median 14, p75 24, p90 41). It blocks new focus on the crowded upper tail while preserving exploration below it. Counts include pending demand because approving a backlog later should not hide today's concentration. This calibration sample deliberately favors recognizable/high-frequency subjects and is not a population percentile for every subject in the world. Recompute counters after verified deltas/cleanup; never retire a valid old fact to meet this threshold. A threshold change requires an explicit policy revision with measured yield/coverage effects.

At run start, aggregate counters/history once from the checked corpus plus existing admission evidence. Refresh only bounded revision deltas; a candidate loop must not reload the whole bank. Persist trustworthy new identity/clock evidence through the signed path; use compatible existing fields if sufficient. A new migration may be prepared in Phase 2 if needed, but none is authorized for production here. Do not backdate new evidence or redo the old feature backfill.

Subtopic rotation: keep the existing nine categories and eight briefs/category. Give every eligible category one batch opportunity before giving any category a second; rotate the starting category with a stable UTC-day/operation ordinal. Rank subtopics by the tuple `(successful admissions in last 30 days, nonretired inventory count)`; rotate ties by UTC day and category, instead of restarting alphabetically each night. Use **up to 3 distinct briefs/batch**, **≤3 accepted per subtopic/run**, and preserve the 20-call ceiling. Prefer unattempted briefs before cycling within a run. Record allocations, attempted/admitted subtopics, blocked reasons and metadata coverage. Unknown legacy subtopics are not zero confirmed historical use.

Each category has a versioned local rotation of region/genre/era lenses where meaningful: rotate a lens by day/brief ordinal, include at least one lens outside Europe/North America in each applicable three-brief allocation, and do not allocate the same three-brief/lens tuple on consecutive UTC dates if alternatives are eligible. Music rotates jazz/classical/world/folk/theory/instruments/blues/recording; literature rotates world/poetry/drama/movements/nonfiction/translation/settings/non-Anglo authors. Use the existing curated topic lists for the other categories. Lenses steer and measure generation; do not claim verified geography/era coverage from unsupported labels or impose a 30-day genre exclusion. No second AI judge or blanket paid tagging.

## 3. Player selection contract

For each existing **15-question** request (also honor the existing 1–100 internal limit), work only inside the candidate pool already read by `lib/trivia.ts`. Initial rule: **no repeated identified primary person/group/work** in a selection. A multi-subject question reserves all its keys. Apply across category boundaries and across unseen/seen tiers. Unknown legacy and generic rows are eligible, each counted as unknown/generic rather than fabricated distinct entity identities. Never promise universal subject uniqueness for such a selection.

Preserve unseen preference: select from unseen eligible candidates first; use seen eligible candidates only to fill the remaining slots. Preserve round-robin category balance among categories with subject-compatible candidates. When all nine categories have enough mutually compatible unseen supply, each gets 1–2 questions in a full selection; with a category filter, every row stays in that category. Use bounded reconsideration of choices in the same pool if a greedy multi-subject choice blocks a fillable selection; Phase 2 must freeze its computational ceiling and test the counterexample. No whole-bank refill or unbounded search.

If fewer than 15 subject-compatible candidates are available under those rules, return a shorter selection and an explicit `insufficient_subject_variety` reason with requested/returned counts. Zero is a truthful no-questions state. Do not insert repeated identified subjects to fill it. Wire the server reason into the existing game front door/results so “15 questions” is not promised for a shorter round. If an algorithm cannot prove a fillable alternative within its bounded search, report a bounded-selection shortfall honestly; do not claim the bank is empty. Report known/unknown coverage to operator diagnostics, not technical metadata in player copy.

No new recent-subject player-history extension in v1: **0 extra history queries, 0 extra stored history, 0 extra provider calls**. The existing answered-question history (up to 10,000 question IDs) stays intact. Preserve venue presence, session/scoring/reward/quota behavior: 45 questions/hour, 2 points/correct, existing bypass rules. This phase does not authorize changing GET authentication or pool filters as collateral work. If compact trusted subject evidence needs selecting, measure bytes before Phase 2 implementation; default to local conservative classification from already-read content and zero extra columns/reads.

## 4. Backlog dispositions and authority

Every frozen target ID gets one final disposition or an explicit unfinished-work entry. A normal `duplicate_review_status='clear'`, empty match list, generated label or old page count is not audit proof.

| Outcome | Required evidence / behavior |
| --- | --- |
| `active` | Current content/hash, complete current retrieval, every required comparison verified unique and candidate sound under unchanged fact policy; fresh signed, revision-bound activation authority |
| `retired_repeat` | Direct high-confidence duplicate evidence against a sound retained active keeper, or a proven reservation/family authority; preserve ID/content/history/references, before state and undo |
| `hold:factual_uncertainty` | Ambiguous scope, contradictory/invalid premise or answer; no approval or repeat deletion inferred |
| `hold:subject_identity_unresolved` | Identity/role remains uncertain where required for new generation; legacy tagging uncertainty alone is **not** grounds to reject a fact-valid backlog row |
| `hold:provider_unavailable` | Missing config, timeout, provider/schema failure; operational failure is not a duplicate decision |
| `hold:evidence_incomplete` | Missing comparisons, retrieval overflow, stale content, low confidence or unverified quality; preserve outstanding work and resume evidence |
| `hold:reservation_review` | Conflict with retired history without a verified usable keeper/reservation chain; never restore or erase history to make a keeper pass |
| `not_processed` | No complete classification yet (budget/time/operator stop); report separately from audited holds |

Concentration/cooldown are new-generation restrictions, **not backlog fact-invalidity rules**. A distinct sound old question can become active even if its subject is crowded. Fact-uncertain and operational holds need separate reason codes and retry policies. Held legacy rows stay outside the ordinary ready-to-review queue; ready means current content-bound positive proof, not a flag set by an old script. Keep hold state separate from player-facing active status and preserve any current hold/provenance history.

Pending-only families need a narrow new atomic operation. Choose a sound canonical representative using verified quality, existing references, date and stable ID as tie-breakers; ranking is never proof. Each loser must have its **own direct** high-confidence sound duplicate proof against that keeper. A–B and B–C cannot authorize C→A. Validate the keeper's fact/soundness against the rest of active, pending and retired memory. Family siblings may be excluded only by signed, content/hash/revision-bound direct proofs, never arbitrary caller ID exclusions. Filtering siblings can expose additional retrieval contenders: recompute compatible bounded retrieval and check those too. Commit keeper activation, loser retirement, reservation links and journal atomically; rollback all if any hash/status/reference drifts. A deleted historical reservation is not disposable family membership.

Reuse identical valid pair judgments for activation; recompute current retrieval, quality orientation and freshness and issue new short-lived signatures. A cache is not a saved activation signature. Keep journaled per-row statuses, content/state hashes, original cohort membership, keeper/reservation IDs and every committed result. Bulk output must report saved IDs/counts, repeats, holds, concurrent changes and untouched IDs even when a later item fails.

## 5. Frozen exit gates for subsequent phases

1. Every synthetic identity expectation passes; zero distractor/generic/royal-title false blocks; aliases/diacritics/initials work; ambiguous surnames/titles remain unknown. Test works/creators, cross-category and multi-subject blocking independently of fact identity.
2. Cooldown at 29 days, exactly 30 days, 31 days; active/pending/deleted/held history; invalid/future timestamps; status-only transitions; content edits and previously concentrated artists under new song labels. Exactly 23 prior occurrences allows a candidate subject, 24 blocks it (subject to other gates).
3. Deterministic successive-day fixtures change tied brief allocations; all eligible categories get an opportunity before repeats; accepted subtopic/run ≤3 and identified subject/run ≤1. Subject rejections make **zero paid comparison calls**. Extra generation prompt/label tokens fit the existing global cap.
4. On the same offline player seeds/pools as the baseline, **zero repeated identified keys**, no unseen-preference regression, correct category bounds when compatible supply exists, honest unknown counts and explicit shortfall behavior. Include adversarial multi-subject choices and category/unseen tradeoffs; never silently fetch a larger pool.
5. Audit every target through active/retired/cache-first comparisons, correct directional quality, no transitive grouping, and no unchecked `clear` path. Every family preserves exactly one approved sound representative or stays held; atomic rollback/idempotency/undo/concurrency verified in isolated SQL. Fix local-only PGlite test loading for CI in Phase 2.
6. Global cap survives restarts/concurrent workers, reserves before transport, charges lost calls in full, prevents stale lock takeover, bounds retries and stops queueing on failure while draining in-flight reservations. A partial batch preserves truthful committed counts.
7. Existing held-out uniqueness release gates remain unchanged (zero duplicate/uncertain admissions; ≥95% distinct acceptance in both splits). Run affected tests, typecheck, lint, full tests and build for Phase 2; build/typecheck sequential. No real credentials in regression tests.
8. Phase 3 reconciles **7,083** snapshot target IDs with later concurrency explicitly; no predicted survivor count becomes an approval. Phase 4 verifies production checks and independent readback; Phase 5 proves real positive paths within a newly approved allowance. Phase 6 records seven useful-yield observations and compares costs/coverage/selection with these baselines. Seven empty runs do not establish useful generation.

Budget numbers, cache scenarios and inventory limitations are frozen in [Phase 1 evidence and cost design](speed-trivia-variety-phase-1-evidence.md). Passing these preparation gates authorizes no paid calls, migration, deployment or bank mutation.
